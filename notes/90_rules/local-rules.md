## 1. 共通ルールを上書きする点

| 見出し | 共通ルール | このプロジェクト | 理由 |
|---|---|---|---|
| ワークフロー原則 ＞ 修正は1点ずつ、確認を重視 | commit は、そのつど「commitして」と指示されてから行う。指示は1回きり有効 | 作業のまとまり（下の「commit・push の単位」）が終わるたびに、AI が指示を待たずに commit し、続けて push する | 資料は HTML を正とし、1つの変更が小さく戻しやすい。公開は GitHub Pages で、細かく反映したほうが差分を追いやすい |
| 確認と失敗 ＞ 重大な操作の確認方法 | `commit` と `push` は別の指示。「pushして」と明示されたときだけ push する | commit のあと develop へ push するところまでを、同じ流れで行う | commit だけが手元に溜まると、公開ページと資料がずれる |

**上書きしないもの**: `git reset`・履歴の書き換え（`--amend` を含む）・force push・ブランチやタグの操作は、従来どおり内容を示して確認を取る。載せるファイルは名指しして `git add` し、`-A` ・ `.` は使わない。commit の前に `git diff --cached --name-only` で一覧を見る。

## 2. commit・push の単位

次のどれか1つが終わるたびに、commit して push する。2つ以上を1つの commit に混ぜない。

- 1つの資料（`01`〜`03`・`A1`〜`A3`・`ZZ`・資料一覧・サンプル説明）の本文の修正
- 共通 CSS（`docs/css/style.css`）の変更
- サンプル（`docs/samples/`）の追加・修正
- 名前の変更・移動（リンクの書き換えまで含めて1つ）
- 初期化・設定ファイルの変更

commit の前に、全資料のリンク切れ（`html2md`）・コントラスト（`check-contrast`）・Markdown の表示（`check-markdown`）を通す。失敗したまま commit しない。push のあとは、公開ページの作り直しが終わり、変えたファイルが公開 URL に入っていることを確かめてから報告する。

メッセージの先頭行には、何をどうしたかを書く。件数を書くなら、書く直前に `git diff --cached --name-only` で数える。

## 3. 踏んだ落とし穴

- **`html2md` は `--dir docs` を毎回付ける**。付けないと、docs の資料が変換対象から外れ、README 側のリンクが `.md` から `.html` に戻る
- **資料を追加・改題したら `tools/20_build/update-nav.ps1` を実行する**。前へ・次へ・目次のバッジは、各資料のタイトルバーの見出しから作る。手で直さない
- **資料のファイル名を変えると、公開 URL が変わる**。旧 URL は 404 になる
- **`docs/samples/` の cmd は SJIS ＋ CRLF**。直すときは `convert-encoding <path> --to utf8` → 編集 → `--to cmd` の順に行う
- **サンプルを実行するとコンソールのコードページを継承する**。ログの日本語は、実行した窓のコードページで決まる。検証は窓を SJIS（932）にして行う
